# THE LAST ARK — Agent 1 策划交付说明

> **2026-10-18 更新**：本轮底板已实现四关，逐关地图、数值与验收以 [`LEVEL_DESIGN.md`](LEVEL_DESIGN.md) 为准；本文件保留为单关验收原则、容错设计与回放要求。共享契约为 v0.2.0（v0.1 的可选扩展）。

状态：候选方案，尚未运行物理模拟或双人试玩；坐标、力度、入港阈值必须经回放验收后冻结。
接口依据：`src/shared/contracts.ts`，`CONTRACT_VERSION = '0.1.0'`。当前仅交付策划文档；后续由策划 Agent 在约定目录产出 `levels: readonly LevelSpec[]`。用户未提供实际视觉参考图，不应声称已经参考某张图。

## 1. 本轮范围与体验目标

四小时只打磨一个可重试、可通关的单屏关卡。表现优先级为视觉表达 > 剧情呈现 > 玩法复杂度，但可运行、规则稳定、实际可通关是验收底线。禁止把视觉投入兑换成失效的输入、没有胜负判定或未经实测的关卡。

玩家是两名无法直接驾驶人类方舟的观察者。两人操纵引力与斥力，协助方舟绕过遗迹星体，进入最后一座仍有信标的空间港。探索来自试探力场、选择位置与共同修正航线；不增加搜集品、分支剧情、复杂解谜机关或第二张地图。

剧情限于开局两句、三至四条短提示、成功一句和三种失败反馈；文案与物理数据分离，使用 `NarrativeSpec`。画面主体始终是方舟、两位观察者、危险星体和终点关系。

## 2. 单屏地图候选

逻辑世界为 1200 × 720，坐标原点在左上，x 向右、y 向下；单位为 px、s、px/s、px/s²。屏幕缩放使用等比留边，禁止修改逻辑世界尺寸来适配浏览器。

- 方舟 `ark-01`：中心 (150, 400)，速度 (58, 0)，碰撞半径 10；`receivesPlayerFields = true`、`receivesGravity = true`、`motionResponse = 1`。玩家不得直接修改其位置或速度。
- 危险星体 `planet-01`：中心 (600, 390)，速度 (0, 0)，碰撞半径 78；紫色、`kind = 'planet'`、`hazardousToArk = true`。`receivesPlayerFields = true`、`receivesGravity = true`、`motionResponse = 0.002`。
- 演示陨石 `asteroid-01`：中心 (760, 550)，速度 (-4, -2)，碰撞半径 18；灰色、危险、接受玩家力场和天体引力，运动响应为 1。位置在主航线外，便于验证排斥技能对其他天体生效，不要求每次通关都必须清理它。
- 空间港 `dock-01`：中心 (1070, 400)，半径 100，最大安全入港速度 45。绿色圆环；整个方舟碰撞圆位于港内且速度 ≤ 45 才胜利。
- 吸引者 `attractor`：中心 (330, 230)，半径 14，移动速度 260。
- 排斥者 `repulsor`：中心 (110, 550)，半径 14，移动速度 260。

星体自带引力候选为 `radius = 340`、`strength = 100000`、`softening = 100`、`maxAcceleration = 16`。吸引者候选为 `radius = 280`、`strength = 2000000`、`softening = 70`、`maxAcceleration = 95`；排斥者候选为 `radius = 340`、`strength = 2500000`、`softening = 85`、`maxAcceleration = 90`。以上均是调参起点，不能作为“已验证可玩”的证据。

物理候选：`fixedDt = 1 / 60`、`maxBodySpeed = 220`、`maxTotalAcceleration = 160`、`maxCatchUpSteps = 6`，`seed = 1042`。单帧墙钟 delta 上限 0.1 秒，短时卡顿超过追赶预算时丢弃多余累计时间，避免死亡螺旋；不允许把一个大 dt 直接传给物理。力场使用主协议约定的软化反平方向量公式与半径边缘平滑，不得另行省略衰减项。

大型星体不是静态装饰。它同时发出引力并接受玩家力场，以很低的 `motionResponse` 近似保持位置；这是一项游戏化简化，不等同于真实质量力学。航线评估必须使用它的实时位置。星体不受自身引力。`motionResponse = 0` 只用于明确声明不可移动的装饰，本关不使用。

## 3. 有容错的双人引导路径

建议上方绕行，参考走廊为 (150, 400) → (410, 230) → (760, 220) → (940, 350) → (1070, 400)。这些是宽松的引导区域，不是物理吸附点、自动导航轨迹或强制路线；下方绕行若能安全入港也必须允许胜利。

1. **准备**：`ready` 时允许两名玩家调整位置，方舟与天体不推进。按 Space 后发射。页面明确显示双方键位，准备阶段不能提前把引力作用到方舟。
2. **抬升**：蓝色玩家位于方舟右上，提供上方偏转；金色玩家位于左下，提供向上推力。目标是在到达中央星体前进入 y≈200–250 的宽走廊。无需同时精确切换技能，允许短促施力、观察和调整。
3. **通过**：在中央星体上方保留至少约 50 px 的额外碰撞余量；参考中心距 ≥ 140。玩家跟随方舟移动，释放不需要的力场，利用惯性穿过。两人始终可以同时作用于同一天体，效果矢量叠加。
4. **回落**：通过 x≈780 后，蓝色玩家移到方舟右下，牵引向港口方向；金色玩家移到方舟前方准备减速。
5. **减速**：在港口左侧提前分工：金色玩家站在方舟右侧，将船向左推以降低向右速度；蓝色玩家提供小幅位置修正。靠近港口时避免持续把船拉向港中心而不断加速。
6. **入港**：方舟完整碰撞圆处于空间港内且速度大于阈值时，`dockOverspeed = true`，仅显示警告；继续模拟并允许玩家减速、离港后再进港，或在港内减速到阈值后成功。它不是第四种失败原因，方舟仅部分进入港口时也不设置此警告。

容错来自足够大的港口、宽的绕行走廊、可在准备阶段定位、随时暂停观察和一键重试。暂停冻结玩家与天体；继续时不补算暂停期间的时间。R 从任何状态回到原始 `ready`，恢复配置中的全部位置和速度、事件状态与提示状态，`runId` 增加、tick 归零。

无干预基线必须实测为碰撞、越界或无法安全入港，不能通过仅在描述中声称“必须合作”完成验收。本轮不设计“必须两人同时按下才开门”机制；允许熟练玩家用单个力场通关，但验收必须包含明确使用双方力场的可复现解。

## 4. 最小剧情文本与提示 ID

`title`：静默信标。

`briefing`：

- “方舟已失去转向能力。它载着最后的人类，正滑向死寂的星体。”
- “你们无法触碰飞船，只能改变它周围的引力。远处那圈绿光，仍在等待。”

`hints`：

- `route-up`：“蓝色在前方牵引，金色从下方推离；为方舟留出绕行空间。”
- `pass-north`：“航线已经抬高。松开力场，观察惯性，再决定下一次修正。”
- `approach`：“空间港在右侧。一个修正位置，一个提前站到前方减速。”
- `slow-dock`：“速度仍然过快。金色站到船头方向，推回它的速度。”

`success`：“信标重新亮起。人类还没有走到终点，但终于有了下一站。”

`failure.collision`：“方舟撞上了天体。重试时更早改变航线。”

`failure.consumed`：“方舟越过了无法返回的边界。”（接口保留；本关未放置黑洞。）

`failure['out-of-bounds']`：“方舟漂离了信标覆盖区。重试时提前减速。”

提示触发由开发 Agent 的游戏规则决定，策划只提供 ID 与内容。建议根据第一次越过区域或首次超速入港确定性触发，禁止由渲染帧率或粒子状态触发；是否切换提示不得影响胜负逻辑。未触发的提示可在 README 中作为攻略说明。

## 5. 与其他 Agent 的交付接口

Agent 1 负责 `src/levels/**` 与本设计文档，提交 `LevelSpec[]` 和中文 `NarrativeSpec`；世界坐标、碰撞半径和能力参数均来自配置。当前任务只写本文件，实际配置在开发阶段按共同计划创建。

Agent 2 从 `RenderFrame.snapshot` 读取世界和对象，从 `RenderFrame.narrative` 读取文案，根据 `hintId` 展示已触发提示。视觉半径与碰撞半径可有区别，但危险轮廓必须清楚；装饰不得遮蔽空间港、方舟或力场边界。不得通过画面写回方舟位置或借动画改变入港时机。

Agent 3 独占 `physics/`、`game/`、`input/`、`main.ts`、集成测试和项目配置。Agent 1 提交候选地图与回放要求，Agent 3 返回实测失败原因、通关 tick、最小障碍间距和入港速度，再由 Agent 1 修改关卡数据。共享契约变更需要负责人统一合并并升级版本；不允许多人各自改字段。

已约定的唯一物理语义以 `docs/AGENT_PROTOCOL.md` 第 5 节为准：使用带软化距离和 `max(0, 1-r/R)²` 边缘平滑的力场公式；每个源限幅 → 合向量乘 `motionResponse` → 总加速度限幅 → 半隐式 Euler 更新速度 → 速度限幅 → 更新位置。先从同一时刻的位置计算所有天体加速度，再统一积分。玩家按自身半径夹在世界内，方舟完整碰撞圆越界即失败；方舟与危险天体使用相对运动扫掠圆碰撞，避免高速跨过小障碍。本文件不另行定义公式或物理次序。

## 6. 60 Hz 回放与可通关验收

可通关证据必须来自实际 `GameRuntime`，不能由渲染层拖动飞船、临时改速度、跳过障碍或编造结果。使用同一 `LevelSpec`、`seed`、契约版本及离散 `InputFrame` 序列重新执行。每帧记录吸引者与排斥者的 `move` 和 `fieldActive`；命令作为有序边沿记录，在目标 step 前执行。

回放建议放在 `tests/fixtures/level-01-coop.json`，由开发 Agent 定义文件类型。最少包含配置标识/摘要、固定步长和按运行调用顺序排列的动作；每个动作可表示“命令 + 连续 N 次相同 InputFrame”。不要只用 `snapshot.tick` 当所有操作的时间轴，因为 `ready` 中可以移动玩家，而 tick 不增加。录制准备状态的调用顺序，或在开始录制后才允许 reposition，不能遗漏准备阶段坐标。

执行以下验收：

1. **无干预基线**：从原始配置开始，双方不移动、不施力，发出 start 对应的 `toggle-pause`，运行至终局或 60 秒，断言未胜利并记录原因。若基线胜利，优先调整地图或初速度。
2. **双人通关**：录制双方移动和施力的可操作路线，必须出现双方对方舟有效施力的 tick；重放至 `won`，断言方舟完整进港、速度 ≤ 阈值，且所有状态有限。禁止在测试中直接注入通关位置。
3. **时机容错**：在已通过回放上，将关键施力开始/结束时间各偏移 ±12 tick（0.2 秒），至少尝试三组变化并报告成功比例；失败则调宽走廊、降低初速或扩大港口，不应只精修原回放到一条脆弱解。
4. **一致性**：同一回放重置后运行三次，终态与事件顺序相同；再由宿主以 30/60/120 Hz 渲染节奏驱动同一固定步序列，物理结果一致。
5. **机制覆盖**：双方技能影响陨石和低响应大星体；玩家不受天体引力；双方可同时移动；暂停时状态不变；R 之后重新执行回放仍能通关。
6. **人工双人试玩**：真实键盘验证 WASD+F 与方向键+Enter 同时按键，观察键盘硬件冲突及提示可读性。自动化浏览器测试不等同于完成这项验收。

策划接收的实测摘要须包含：提交版本、参数配置、通关用时、入港速度、最小障碍间距、各容错回放结果、已执行/未执行项目。首次真实运行前，README 与交付说明不得写“可通关已验证”。

## 7. 四小时个人安排与冻结点

时间以实现阶段开始 T+0 为准，不把本轮制定协议的耗时计入四小时实现窗口。

- **T+0–15**：锁定一个关卡、三句故事意图和对象清单，按主协议已冻结的力场公式及 response 次序配置参数。T+15 交付可被类型检查的第一版 `LevelSpec`，视觉 Agent 同时可使用相同场景。
- **T+15–45**：基于灰盒模拟调整起点、中央障碍与港口位置，完成无干预基线；输出第一版提示 ID 和候选双人路线。
- **T+45–60**：与开发协作取得首条回放，T+60 必须已有能运行的单关卡与明确的通关/未通关状态。此时不再增加星体类型、关卡或故事分支。
- **T+60–120**：进行双人通关与 ±12 tick 容错调整；收敛参数，不改接口形状。T+120 冻结关卡结构、对象 ID、空间布局与文案，只有阻塞通关的参数允许继续改动。
- **T+120–180**：配合视觉联调，检查美术危险轮廓与物理轮廓一致、提示不遮挡；执行最终地图回放并补充 README 攻略、已测/未测清单。T+180 冻结内容。
- **T+180–210**：重试、暂停、入港与失误路线回归，修复可玩性缺陷；由集成负责人完成最终构建和浏览器检查。
- **T+210–240**：只处理阻塞发布的问题，配合仓库交付与试玩说明；没有新增关卡、额外剧情或新规则。

## 8. 失控时的降级规则

- **T+60 未收敛**：将演示陨石移远主航线，但地图内至少保留一颗可见、可受两位玩家力场影响的移动陨石实例；将星体自引力适当降低，把方舟初速从 58 下调到 45–50，先获得中央单障碍绕行解。不删除两位玩家、碰撞或港口速度条件。
- **T+120 未通关或依赖极精确时机**：扩大港口半径至候选 115、降低初速、向下移动中央星体以扩宽上侧走廊，并减少剧情提示至开局/接近港口两条。参数修改后必须重跑无干预基线，防止自动通关。保留超速警告与低速成功判定。
- **T+180 仍有阻塞**：冻结所有视觉新增与文案润色，三人集中检查最小关卡；可关闭非必要粒子、后处理与动态背景，保留颜色、危险边界和基本反馈。优先提交经测试的单关原型；若最终仍不能通关，必须如实报告未完成，不以录屏或静态画面代替。

Agent 1 不负责自行 Commit/Push 或更改仓库设置；由主集成负责人按用户已授权范围统一发布，避免共享工作区出现并发提交。
